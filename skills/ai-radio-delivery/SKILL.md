# AI 电台节目制作 Skill

使用本 skill 时，目标是交付一条可直接播放的电台节目成品，而不是只交付文案或素材。Agent 必须按节目结构、音乐关系、混音比例、验证规则执行；不达标时只能标记为阶段结果，不能写成“已完成”。

## 核心原则

- 先设计节目结构和时间线，再生成音频。
- 主持人、背景音乐、歌曲、音效都必须作为独立资产保存。
- 背景音乐要服务内容，不能和主持人抢耳。
- 背景铺底音乐不要一次请求 300 秒。优先生成 `30-90` 秒无人声纯音乐，再由混音脚本循环铺满节目时长，避免长请求超时。
- 结尾歌曲或配歌可按需求单独生成，例如 `30` 秒。
- 云端音乐接口返回 `504`、超时、HTML、JSON 错误或任何非音频内容时，不能把无配乐版本标记为完成；必须把已生成资产和失败原因写入交付说明，等待用户重试或继续。
- 电台开头必须先有音乐或环境氛围。前 5 秒不得出现主持人口播；主持人第一句建议在 6-10 秒进入，最晚不得超过 15 秒。
- 口播一致性不靠“一次生成所有内容”解决。优先分段生成，但必须通过**声线锁定协议**（见第四章第 3 节）锁定同一个主播音色。**`[控制:xxx]` 文本描述不锁定音色**——相同描述文本每次调用可能生成不同声线，不能只靠它“保持一致”。
- 声线锁定的两条可靠路径：**固定 Speaker**（Qwen3-TTS `custom_voice`，同名 speaker = 同声）或**克隆锁定**（第一段生成后上传，后续段落用 `voice_clone`/`zero_shot` 克隆第一段参考音频）。
- 不要把无固定 `speaker_id`、`voice_id`、`seed` 或参考音频的 voice design 接口当作同一主播的分段 TTS 使用；这类接口可能每段重新设计声线。
- 结尾不能干停，主持人收束后应有音乐尾巴或淡出。
- 用户要求 5 分钟时，最终音频不得短于 295 秒；不达标不能标“完成”。
- 最终 `deliverable_manifest.json` 的 `primary_path` 必须指向文本说明文件，音频文件放入 `files` 列表给页面播放器展示，不能把 MP3/WAV 当主文本交付物。
- 用户要求导出时间线轨道时，必须额外交付多轨道 XML，包含字幕轨，供用户后续剪辑编辑。
- 导出 Premiere / PR 可用 `timeline_tracks.xml` 时，必须同时遵守 `premiere-xml-timeline` skill；该 skill 是 XML 结构、媒体描述、波形可见性和 PR 导入兼容性的主规则。
- 不要使用 PowerShell 混音脚本。混音必须使用本 skill 的 Python 脚本 `scripts/mix_ai_radio.py`，或等价 Python 实现。

## 一、节目结构设计

一个完整的电台节目通常包含以下部分。

1. 开场：`0:05-0:15`
   - 背景音乐淡入，先建立节目氛围。
   - 前 5 秒不得出现主持人口播。
   - 主持人第一句开场白建议在 6-10 秒出场，最晚必须在 15 秒内出场。

2. 引入主题：`0:15-2:00`
   - 主持人简要介绍本期节目主题。
   - 背景音乐保持低音量作为垫乐。

3. 主体内容：`2:00-结束前 2 分钟`
   - 主持人讲述核心内容。
   - 可穿插 1-2 段音乐或歌曲作为情绪过渡。
   - 长节目每 8-12 分钟设置一个小高潮或情绪转折点。

4. 情绪高潮段落
   - 选择一首与主题契合的歌曲或音乐片段作为情绪拉升。
   - 歌曲或音乐结束后，主持人回归，做情感总结。

5. 结尾：节目结束前 `1-2 分钟`
   - 主持人做节目总结和收尾。
   - 背景音乐渐强，主持人语速放缓。
   - 音乐淡出结束，最后可留 1-2 秒自然尾音。

## 二、背景音乐与主题配合

1. 音乐情绪与内容一致
   - 温情话题：舒缓钢琴、弦乐、轻柔氛围音乐。
   - 励志话题：有节奏感的轻摇滚、电子、明亮流行。
   - 怀旧话题：经典老歌、爵士、复古质感音乐。

2. 音乐分段使用
   - 开场：用完整前奏或纯音乐建立氛围。
   - 段落过渡：用短音乐片段或音效衔接。
   - 情绪拉升：选完整歌曲或明显更饱满的音乐段作为节目高潮。

3. 避免音乐与主持人抢耳
   - 主持人讲话时，背景音乐优先使用无人声纯音乐。
   - 如果带人声歌曲出现在主持人下方，必须大幅降低音量。
   - 情绪高潮歌曲可正常播放，但主持人回归前要淡出或留自然尾音。

## 三、音乐与主持人音量比例

以下标准是制作目标，实际执行时可通过 `ffmpeg volumedetect` 或听感微调。

1. 主持人独白时
   - 背景音乐：约 `-18dB` 到 `-24dB`。
   - 主持人声音：约 `-6dB` 到 `-3dB`。
   - 比例约 `1:4` 到 `1:5`，音乐只做氛围底衬。

2. 主持人开场或收尾
   - 开场前几秒：音乐可到 `-6dB`，无主持人。
   - 主持人进入：音乐降至约 `-18dB`，话音约 `-3dB`。
   - 开场音乐应先以接近全量或节目设定主音量建立氛围；主持人第一句进入前约 `2` 秒开始平滑拉低，不能在主持人开口瞬间硬切。

3. 纯音乐或歌曲时段
   - 歌曲或纯音乐：约 `-1dB` 到 `-3dB`，保留动态余量。
   - 如果歌曲后紧接主持人，歌曲末尾 3-5 秒开始淡出。

4. 情绪高潮段落
   - 歌曲进入时保持正常播放音量。
   - 歌曲结束后，主持人讲话前留 1-2 秒空白或混响尾音。
   - 主持人回归后，音乐恢复到约 `-18dB` 的垫乐音量。

5. BGM 动态起伏
   - BGM 不能整段固定一个低音量。它应随节目内容做自动音量曲线：无口播时回到较完整音量，有口播时降低为垫乐。
   - 主持人即将开口前约 `2` 秒开始 duck，下降过程要平滑；主持人停止讲话后的 `1-3` 秒内逐步回升，不能突然抽掉或突然冲上来。
   - 段落停顿、转场、情绪句、主题升温和收尾祝福处，BGM 可以短暂抬高 `3-8dB` 或切入更饱满片段，形成情绪推动。
   - 检测到静音、长停顿或口播间隙时，BGM 应回到原设定主音量，避免出现“人没说话但音乐还被压着”的空洞感。
   - 情绪拉高时也不能盖住人声；如人声同时存在，优先保证人声清晰，BGM 只做托举。

## 四、制作流程

1. 准备素材
   - 根据用户主题生成主持人稿件文案。
   - 根据主题情绪推荐并生成背景音乐或歌曲。
   - 背景铺底音乐按 `30-90` 秒生成，必须是适合口播下方铺底的无人声纯音乐。不要为铺底音乐直接请求整期节目长度。
   - 如果需要结尾配歌，单独生成短歌或短音乐片段，通常 `30` 秒即可。
   - 音乐生成失败时，记录请求、响应状态、错误正文和已完成资产；不要继续伪造本地音乐，也不要把任务写成已完成。
   - 使用 Soundao 云端 TTS 生成主持人语音。
   - 如果用户指定不要某个引擎，必须遵守。
   - 不要把整期节目一次性塞给 TTS 生成。应按开场、主题引入、主体、情绪转折、收尾拆成 4-8 个自然段，分别生成并检查，再拼接。
   - 不要把不被当前 TTS 引擎明确支持的情绪标签直接写进文本。若引擎只支持普通文本，应把情绪写入可用的 `instruction`、`prompt`、`style` 或等价字段；没有这些字段时，用标点、短句、自然停顿来表达。
   - 主持人声音如果听起来僵硬、机械、过快、过平或像念说明书，必须调整文案和 TTS 参数后重生成，不能直接交付。
   - 电台主持优先选择支持情绪、语气、停顿或指令式控制的 TTS；只有在用户要求“快速预览”时才使用最基础音色。
   - 生成后保存请求 JSON、响应元数据和音频文件。
   - 建议转码为统一采样率音频后再混音；最终导出 MP3 或 WAV。

2. 判断修改任务与资产复用
   - 开始生成前先判断本次是全新创作、修改上一版，还是继续未完成任务。
   - 如果输出目录或上一轮结果中存在 `previous_run_context.json`、`task_context.json`、`deliverable_manifest.json` 或旧资产，必须先读取并写出 `reuse_plan.json`。
   - 如果页面提交了“修改意见”或 `revision_notes`，本次必须按修改模式处理。修改意见不改变原任务要求，只说明基于上一版要改哪里。
   - `reuse_plan.json` 至少包含：任务分类、变化项、未变化项、可复用资产、必须重做资产、只需重新混音/校验资产、判断理由。
   - 节目主题、节目长度、听众地区、开场播报、主播声音、配乐风格、结尾安排、节目要求任一变化，都要评估影响范围。
   - 口播稿某一段变化，只重做该段口播；`voice_profile.json` 或主播声音要求变化，则重做全部口播。
   - 配乐风格、BPM、情绪或时长没变时可复用背景音乐；结尾安排、歌词或风格没变时可复用结尾配歌。
   - 只要口播、背景音乐、结尾配歌、节目时长或时间线任一变化，都必须重新混音并重新生成 `validation.json`。
   - 如果用户请求导出时间线轨道，只要口播文本、字幕、素材文件、时长或时间线任一变化，都必须重新导出 `timeline_tracks.xml`。
   - `deliverable.md`、`deliverable_manifest.json`、`validation.json` 只能作为参考，不能作为最终成品直接复用。
   - 复用前必须确认文件存在、格式正确、可读取、时长合理；否则列入重做。

3. 声线锁定协议（刚性要求）

   生成多段口播时必须遵守本协议。不遵守将导致各段音色不一致，听感割裂。

   > **核心禁令**：不要只靠相同的 `[ 控制:xxx ]` 文本描述来“保持一致”。相同描述文本不保证相同音色，每次调用可能生成不同声线。必须用以下两种方法之一锁定音色。

   ### 方法 A：固定 Speaker（最简单，推荐）

   引擎：Qwen3-TTS，`POST /v1/qwen3-tts/synthesize`

   - `task`: `"custom_voice"`
   - `speaker`: 从 9 个预设音色中选一个（Vivian / Chloe / Ethan / Sophia / …），根据节目需求选择性别和风格。**同名 speaker = 完全相同音色，跨段保证一致。**
   - `instruct`: 每段可以不同，用来调整情绪。例如第一段 `"instruct": "用热情愉快的语气朗读"`，第四段 `"instruct": "用温柔感情的语气述说"`。音色不变，只变情绪。
   - `language`: `"zh"`

   调用示例（每段都用相同 speaker）：

   ```json
   {"task": "custom_voice", "speaker": "Vivian", "instruct": "用亲切自然的电台主播语气朗读", "language": "zh", "text": "欢迎收听本期节目……"}
   ```

   ### 方法 B：克隆锁定（最灵活，可自定义声线）

   适合需要自定义音色的场景。分两步：

   **第 1 步：生成基准声线（只做一次）**

   - 用 VoxCPM 或 Qwen3 `voice_design` 生成第一段口播
   - VoxCPM 可以用 `[ 控制:描述 ]` + `[ 情绪标签 ]` + 正文
   - Qwen3 用 `{"task": "voice_design", "instruct": "描述", "language": "zh"}`
   - 生成后保存为音频文件（如 `host_segment_01.wav`），并记录对应文本
   - 检查音色是否合适；不合适则调整描述重新生成，不要带着错误声线继续

   **第 2 步：后续段落克隆第一段（锁定声线）**

   上传第一段音频到服务器获取服务器路径，然后用克隆引擎生成后续段落。三选一：

   - **Qwen3-TTS `voice_clone`**：`{"task": "voice_clone", "audio_path": "<第一段服务器路径>", "ref_text": "<第一段文本>", "language": "zh", "text": "<本段正文>"}`
   - **CosyVoice3 `zero_shot`**：`{"mode": "zero_shot", "prompt_text": "<第一段文本>", "text": "<本段正文>"}`（需先上传参考音频）
   - **VoxCPM 可控克隆**：使用第一段作为参考音频，加 `ultimate_cloning=true` 极致还原

   > 克隆要求：参考音频 3–10 秒最佳，不要超过 15 秒。第一段太长时用 ffmpeg 截取其中 3–10 秒的一句完整话作为参考。

   ### voice_profile.json 必填字段

   每期节目必须根据用户需求（主题、情绪、性别、年龄感）定制主播档案，不能跨节目复用相同档案：

   ```json
   {
     "engine": "qwen3-tts",
     "lock_method": "fixed_speaker | voice_clone",
     "speaker": "Vivian",
     "voice_description": "温暖亲切的成熟女声电台主播",
     "ref_audio_path": "host_segment_01.wav | null",
     "ref_text": "第一段对应文本 | null",
     "language": "zh",
     "sample_rate": 44100
   }
   ```

   ### 一致性检查

   - 后续每段生成后与第一段对比：音色、性别、语速、响度是否一致。明显漂移时只重生成异常段。
   - 分段拼接前必须逐段统一响度（`loudnorm I=-18` 到 `-16`）和采样率，再拼接。不能只对拼接后的整条口播做一次响度处理。
   - 分段文本要保持同一种主播人写法：称呼方式、句子长度、停顿习惯、情绪表达和节目名读法要统一。
   - 不要把 `[ 温柔 ]`、`[ 自然 ]` 等不被引擎支持的标签直接塞进朗读正文；这些标签应进入可用的控制字段（如 Qwen3 的 `instruct`），或转写成自然标点和停顿。

4. 编排时间线
   - 按“开场、引入、主体、高潮、结尾”自动计算各段起止时间。
   - 标注主持人语音、背景音乐、歌曲或音效的进入和退出时间。
   - 标注情绪高潮坐标，例如歌曲进入点、情绪拉升窗口、收尾起始点。
   - 生成 `cue_sheet.md` 或等价说明文件。
   - 开场时间线必须明确记录：音乐开始时间、主持人第一句进入时间、主持人第一句文本。

5. 调整音量与淡入淡出
   - 按本 skill 的音量比例自动调整。
   - 每个音乐片段首尾添加 1-3 秒淡入或淡出。
   - 主持人片段首尾添加约 0.5 秒淡入或淡出。
   - 必须为 BGM 生成随时间变化的音量曲线：开头全量建立氛围，口播前约 2 秒拉低，口播中维持垫乐，口播停顿或静音时回升，情绪转折和结尾处适度抬高。
   - 不能只用一个全局固定 BGM 音量或简单 sidechain 压缩代替完整编排；sidechain 可作为辅助，但 `cue_sheet.md` 中仍要标注主要 duck、回升、情绪抬升节点。
   - 克隆或多段 TTS 时，检查音高、音色、性别和连续性；明显漂移时只重生成异常段。

6. 混音与导出
   - 必须调用 `scripts/mix_ai_radio.py` 或等价 Python 脚本，不能用 `mix_ai_radio.ps1`。
   - 自动处理主持人延迟、歌曲切入延迟、淡入淡出、垫乐循环、最终时长裁切。
   - 导出比特率不低于 `192kbps` 的 MP3，或按用户要求导出 WAV。
   - 文件命名建议：`节目名称_日期.mp3`。
    - 归档到输出目录或工作区 `02_工作成果/AI电台节目/<result-id>/`。

7. 导出可编辑时间线
   - 如果用户勾选或要求“导出时间线轨道”，最终必须生成 `timeline_tracks.xml` 或等价命名的 XML。
   - `timeline_tracks.xml` 默认必须使用已验证参考版 `Soundao FM：气质的价值` 的 FCP7 XML / `xmeml` 结构，根节点应为 `<xmeml version="5">`。
   - xmeml 必须是 30fps、9000 帧、300 秒；字幕写入视频轨 generatoritem 的 Text effect；音频轨至少包含业务流程要求的音频轨；路径使用 file URL，并把系统路径分隔符规范为正斜杠。
   - 每个 `clipitem/file/media/audio` 必须写完整音频媒体描述：`samplecharacteristics/depth=16`、`samplecharacteristics/samplerate=<实际媒体采样率>`、`channelcount=2`。缺少这些字段时，Premiere 可能导入成无波形静音线。
   - 如果口播原始长度不能放进 300 秒，必须先生成 `host_voice_retimed.mp3` 或重生成更短口播，且 `host_voice_retimed.mp3` 必须转成双声道；不能只改 XML 时间码假装可用。
   - 如果用户明确要求 FCP7、Premiere、达芬奇等剪辑软件专用格式，可以额外生成 `timeline_tracks_xmeml.xml` 或其它格式作为备用，但 `timeline_tracks.xml` 仍保留 Soundao 简单时间线格式。
   - XML 必须是多轨结构，至少包含：
     - `host_voice`：主持人口播轨，按每段口播音频写入起止时间和源文件。
     - `background_music`：背景音乐轨，写入循环或铺底片段的起止时间和源文件。
     - `closing_song`：结尾配歌轨，写入进入时间、淡入淡出和源文件。
     - `subtitles`：字幕轨，按节目稿或口播分段写入每条字幕的开始时间、结束时间和文本。
   - 字幕轨必须覆盖主持人口播的主要内容；不能只写“字幕见稿件”。
   - 同时额外交付 `subtitles.srt`，方便剪映、Premiere、达芬奇等工具在 XML 字幕轨不兼容时单独导入字幕。
   - XML 中同时保存节目帧率或时间基准、总时长、轨道名、clip id、源文件路径或相对路径。
   - 如果无法生成某个源文件，XML 里不要伪造该轨道；交付说明必须说清楚缺失原因。
   - `deliverable_manifest.json` 必须包含 `timeline_xml_path`，并把 XML 文件加入 `files`。

8. 成品验证与交付
   - 用 `ffprobe` 检查文件时长、码率、文件大小。
   - 用 `silencedetect` 检查异常空白。
   - 面向 WebUI 播放交付时，必须确认页面播放器能正确识别成品时长；如果 MP3 在浏览器里显示时长异常，应额外转封装/转码为浏览器稳定识别的 M4A，并在 manifest 中把 WebUI 主播放文件指向该版本。
   - 必须确认前 5 秒没有主持人口播。
   - 必须确认主持人第一句在 6-10 秒建议窗口内出现；如果因特殊节目设计延后，最晚不能超过 15 秒，并要在交付说明里解释。
   - 不能只看 cue sheet，要用试听、波形、ASR/人声检测或前 15 秒预览中的至少一种方式验证开场。
   - 必须确认最终时长满足用户要求；5 分钟节目不得短于 295 秒。
   - 必须确认主持人口播本身时长足够，不能只用背景音乐把总时长补到 5 分钟。5 分钟节目中，主持人口播建议不少于 210 秒；主持人口播结束到结尾配歌进入前的空档不应超过 15 秒，除非节目设计明确要求长音乐段并在交付说明中写清楚。
   - 必须检查 `deliverable.md`、`cue_sheet.md`、`deliverable_manifest.json`、`timeline_tracks.xml` 等文本交付物为 UTF-8 中文可读内容；标题、摘要、轨道名、角色名、字幕正文不得出现 `????` 这类问号替代乱码。
   - 如果 XML 字幕轨或交付说明出现乱码，必须从正常中文节目稿重新生成对应文本文件后再交付，不能标记为完成。
   - 最终提交前必须调用项目全局检查工具：`python web_agent_framework/final_delivery_check.py --out-dir <输出目录> --task-context <输出目录>/task_context.json --manifest <输出目录>/deliverable_manifest.json --out <输出目录>/final_delivery_check.json`。只有 `final_delivery_check.json` 的 `ok` 为 `true`，才允许把电台节目回写为完成；否则按 `blocking_issues` 修正后重新检查。
   - 验证通过后输出 `deliverable.md` 和 `deliverable_manifest.json`。
   - 如果任何验证工具失败或有局限，必须在交付报告中明确说明。

## 五、Soundao 云端调用要求

- 先读取 `/llms.txt`，再按任务读取 `/llms/tts.txt`、`/llms/tts-engines.txt`、`/llms/music.txt`、`/llms/audio-tools.txt`。
- 使用 Python `requests` 或项目内 `web_agent_framework/soundao_cloud.py`。不要用 PowerShell、cmd、curl、Invoke-WebRequest 或 Invoke-RestMethod 处理中文 JSON。
- 调用任何付费能力前必须执行 `python web_agent_framework/soundao_cloud.py balance --out <输出目录>/balance_before.json`。
- 最后一次付费调用完成并下载资产后必须执行 `python web_agent_framework/soundao_cloud.py balance --out <输出目录>/balance_after.json`。
- 查积分接口规则：API Key 使用 `POST /v1/auth/balance`；登录账号使用 `GET /v1/auth/me`。优先使用项目封装 `soundao_cloud.py balance`，它会输出统一字段 `credits/balance/remaining_points`。
- `deliverable_manifest.json` 的 `credits` 必须写入 `before`、`after`、`deducted`、`remaining`、`note`。`deducted = before - after`；如果云端响应直接返回扣费，以云端扣费为准。如果任一步失败，能确认的字段照写，未知字段写 `null`，并说明原因，不能编造积分。
- 不得把 API Key、密码、JWT Token、Authorization Header 写入日志、页面、交付物或积分记录。
- 音乐、配音、音效、分析、清理、媒资取回应使用 Soundao 云端能力。本地工具只用于转码、混音、响度处理、文件归档和验证。
- 云端生成结果可能不会永久保存，完成后必须及时下载保存到本地结果目录。

## 六、交付物格式

输出目录必须至少包含：

- `deliverable.md`：给用户看的中文交付说明。
- `deliverable_manifest.json`：页面读取的结构化清单。
- `program_script.md`：主持人节目稿。
- `cue_sheet.md`：时间线和素材编排。
- 主持人语音、背景音乐、歌曲、最终混音等音频资产。
- `validation.json`：时长、码率、文件大小、静音检测结果。
- 用户请求时间线时，包含 `timeline_tracks.xml`：可编辑的多轨道时间线，必须含字幕轨。

`deliverable_manifest.json` 格式：

```json
{
  "title": "节目标题",
  "summary": "一句话说明成品",
  "primary_path": "deliverable.md 的绝对路径",
  "final_audio_path": "最终音频成品的绝对路径",
  "timeline_xml_path": "timeline_tracks.xml 的绝对路径；未请求时为 null",
  "files": ["相关文本、音频、验证文件的绝对路径"],
  "credits": {
    "before": null,
    "after": null,
    "deducted": null,
    "remaining": null,
    "note": "积分未返回时说明原因"
  }
}
```

注意：`primary_path` 不能指向 MP3、WAV、M4A、FLAC 等二进制音频。

## 七、Python 混音脚本

优先使用：

```bash
python skills/ai-radio-delivery/scripts/mix_ai_radio.py ^
  --host-track host_voice_full.mp3 ^
  --bed background_music.mp3 ^
  --song closing_song_30s.mp3 ^
  --output final_radio.mp3 ^
  --duration-sec 300 ^
  --host-delay-sec 8 ^
  --song-start-sec 268
```

脚本会完成：

- 背景音乐循环和淡入淡出。
- BGM 动态音量曲线：开头全量、口播前 2 秒拉低、口播停顿回升、情绪点适度抬高。
- 主持人延迟进入并维持清晰音量。
- 歌曲按本地时间先淡入淡出，再放到最终时间线。
- 最终裁切到目标时长。
- 导出 MP3。
- 输出 `validation.json` 和静音检测日志。

运行后仍要读取验证结果。验证不达标时，必须修复后再交付。
